# Opencast extensions

Opencast extensions are small Raycast-compatible command packages. The extension UI runs inside
Opencast's JavaScriptCore host, while privileged work is performed by typed native capability
providers in the app.

The app does **not** ship Node, Bun, npm, a shell daemon, or one helper process per extension.
Bun is used only by the development bundler when building a package.

## v1 extensions

The first release focuses on three local, native-backed commands:

| Extension | What it does | Capabilities |
| --- | --- | --- |
| Kill Process | Sort running processes by CPU, memory, or name. Kill, force-kill, restart, and force-restart a selected process. | `process.inspect`, `process.terminate`, `process.restart` |
| Ports | List listening TCP ports, owning processes, host, protocol, and user. Copy an address or terminate the owner. | `ports.inspect`, `process.terminate`, `clipboard.write` |
| System Monitor | Show CPU, memory, disk, network, battery, and temperature metrics in native detail cards. | `system.metrics.read` |

Brew is not part of the v1 package set. Its capability bridge remains available for future
third-party extensions, but no Brew package is built or published in v1.

## Runtime model

An extension command has two halves:

1. JavaScript renders the command using the compatibility API (`List`, `Detail`, `ActionPanel`,
   hooks, and capability-backed APIs).
2. Opencast validates and routes every privileged request through the native capability broker.

The extension cannot directly use `child_process`, arbitrary filesystem access, native addons, or
network APIs. Capability declarations are stored in the package manifest and checked again by the
broker before every request. Destructive operations require user confirmation and are bounded by
native providers.

The app owns lifecycle and scheduling. View commands are started on demand. `no-view` and menu-bar
commands are only allowed to run when their declared lifecycle policy permits them, and background
refresh is disabled by default.

## Package layout

An installable `.ocx` package is a directory with this shape:

```text
example.ocx/
├── bundle.js
├── manifest.json
├── capabilities.json
└── build.json
```

- `bundle.js` is the production IIFE generated by the extension builder.
- `manifest.json` declares the extension, command entry points, UI mode, preferences, and capabilities.
- `capabilities.json` records the risk and consent metadata for declared capabilities.
- `build.json` records the bundle hash, size, builder version, and capabilities used by the bundle.

The package validator rejects unsafe paths, native binaries, post-install scripts, undeclared
capabilities, invalid hashes, and bundles larger than 8 MB.

## Build a fixture locally

Requirements: macOS 15+, Xcode 26, Node.js, and Bun. Bun is a build tool only. It is never copied
into the app or the `.ocx` package.

Build one of the v1 fixtures:

```sh
node Tools/extensions/build-extension.js \
  --fixture Extensions/Fixtures/kill-process \
  --out build/extensions/kill-process.ocx \
  --capability process.inspect \
  --capability process.terminate \
  --capability process.restart
```

Equivalent commands are already wired into `make extensions-test` and
`make extension-store-test`.

## Install a local package

1. Build the `.ocx` directory.
2. Open **Settings → General → Extensions → Import Extension**.
3. Choose the `.ocx` directory.
4. Opencast validates the package before moving it into the app's extension directory.

Installed packages can be disabled, updated, rolled back, or removed from the same settings
section. Extension state is isolated by the app bundle identifier, so Debug and release builds do
not share installed packages.

## Test the extension surface

Run the full extension contract and provider checks:

```sh
make extensions-test
make extension-store-test
```

These checks cover host framing, list/detail/form/grid rendering, no-view execution, capability
routing, process and port providers, system metrics, package validation, and tamper detection.

For an app bundle and package budget check, build the app first and run:

```sh
make build
OPENCAST_APP="build/DerivedData/Build/Products/Debug/Opencast Dev.app" \
  make extension-budget-test
```

The budget test verifies that the app bundle contains no extension package or JavaScript runtime and
that each package stays below the 8 MB admission limit.

## Store format

The store has no backend. Release automation uploads `.ocx.zip` assets and a static
`extensions-catalog.json` file to the GitHub Release. The app downloads the catalog only after the
user grants store network consent, verifies the package hash and capability list, then installs it
atomically. See [`Store/README.md`](../Store/README.md) for catalog generation.

## Adding an extension

1. Add a fixture under `Extensions/Fixtures/<name>` with one `package.json` command and its source.
2. Use only APIs exposed by `Extensions/Runtime/opencast-api.js` and the JSX runtime.
3. Declare the minimum capabilities in the build command and package metadata.
4. Add the fixture to the relevant Makefile test target.
5. Add host contract coverage for capability requests, renders, and destructive actions.
6. Run the extension tests and package budget check before proposing store inclusion.

Store admission is intentionally stricter than local import. A package needs a stable source,
license, pinned dependency metadata, supported architectures, capability review, rollback metadata,
and clean validation results before it can be marked verified.
